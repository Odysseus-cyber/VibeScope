# 面试讲解与简历素材

## 两分钟项目介绍

“我做的是一个观察 AI 辅助开发应用趋势的平台。GitHub 用来发现公开项目并记录 stars 等指标，Hacker News 提供项目讨论线索。后台完成采集、去重、分类、日快照和 dbt 分层建模，FastAPI 把固定口径指标提供给 React 页面。AI 负责识别作者的开发声明、提取应用类别和工具，并根据 SQL 事实生成周报。系统同时保留来源证据、分类版本和任务覆盖信息。”

“我重点处理了三类数据问题：同一项目多来源重复出现、候选工具与真正应用作品混杂、增长窗口缺少历史观测。分别用来源主键和精确链接关联、双维分类与人工复核、精确边界快照和 null 语义解决。页面的每个主要数字都有明确的统计池与时间口径。”

## 简历表述模板

- 独立开发 VibeScope 全栈趋势分析平台，基于 Python/FastAPI、PostgreSQL、dbt 与 React 实现公开项目采集、AI 分类、指标服务及周报生成。
- 设计 ODS—DWD—DWS—ADS 数据链路，以 repository ID、HN item ID 和每日复合唯一键处理去重与重复执行，建立数据新鲜度和采集覆盖检查。
- 实现带来源证据的作品分类与人工修正，使用 SQL 事实约束周报，区分观测缺失、真实零增长与负增长。

如需填写规模和性能，只能补入真实测量的项目数量、原始记录数、采集耗时、查询 P95 和评估集指标。不要把演示数据条数写成线上日活，也不要把模板摘要称作模型能力。

## 高频追问

| 问题 | 应回答的工程事实 |
| --- | --- |
| 为什么要数仓分层？ | 原始 JSON 支持溯源；DWD 统一身份和口径；DWS 明确完整性；ADS 给页面稳定指标。 |
| 重复运行会不会重复计数？ | 仓库和 HN 使用来源稳定 ID，每日快照有 app_id+date 唯一约束；当前态更新与原始响应留存分开。 |
| 为什么七天增长为 null？ | 缺少任一精确边界快照时无法计算净增，不能用当前总量代替历史差值。 |
| AI 怎么判断这是 Vibe Coding 应用？ | 先区分作品类型，再判断作者是否明确声明 AI 辅助开发；保存证据片段和模型版本，允许人工复核。 |
| HN 项目怎样与 GitHub 合并？ | 使用明确来源 URL，标题相似只作为候选线索，不直接合并。 |
| 分类修正后历史报表怎样变化？ | 当前图表使用当前正式统计池回看历史观测；已生成报告保存当时事实，不伪装成历史分类快照。 |
| 为什么不用 Kafka/Spark/Flink？ | 首版实际数据量和采集频率由 API 额度决定，单机 PostgreSQL 足够；先测量瓶颈，再按吞吐和延迟需求扩展。 |
| dbt 为什么用视图？ | 限定追踪规模下便于口径更新和人工修正即时生效；规模扩大后可将高频 ADS 转为增量/物化模型。 |
| 如何证明模型效果？ | 已有40条合成规格案例和32条真实来源的AI审读开发样本，保留逐条误判；真实人类标注、独立留出集与外部模型评测需另行完成，不能混称。 |

## 可做的真实测量

在固定配置下记录一次完整同步：来源请求数、候选数、实际收录数、耗时、失败/限流次数。对同一数据库重复运行，比较应用主键数和每日快照唯一性。用固定查询及并发测量 API 延迟，注明机器、模式与数据规模。报告本次测量，避免从单机样本外推生产吞吐。

后续扩展应由证据驱动：API 查询慢时优化索引和聚合物化；单 worker 排队明显时拆分队列；需要多个独立数据源时扩展来源适配器；需要历史成员口径时增加分类有效期维度。
